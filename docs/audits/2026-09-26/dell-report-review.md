# Dell benchmark papers: technical review and missed opportunities

**26 September 2026 • Internal review for Chris • Revised by paper**

These papers could support stronger Dell recommendations by testing feasible, tuned deployments against a defined service and quality target. The largest opportunities are in GPU placement, engine configuration, workload design and the distinction between peak output and useful completed work. Several published contradictions also require correction before the results can support sizing or economic claims.

Each paper has a two-column table, ordered by severity, followed by the experiments that would improve it and the customer benefit those experiments could establish. **Critical** means a central configuration or claim needs correction; **High** can change a purchasing or sizing decision; **Medium** limits interpretation or reproduction; **Low** is editorial. Evidence is labeled **confirmed**, **disclosure gap**, or **tuning opportunity**. Missing disclosure does not prove missing work. Proposed speedups are not measured results.

In the right column, **Current approach** identifies mechanisms verified in this project. **Publication requirement** identifies evidence or controls we need to enforce; it does not claim the internal audit's open defects are fixed. Third-party benchmarking is treated as complete. Its quality results must be attached to the exact deployment being recommended.

Terminology: **TP** splits a model across GPUs; **replicas** serve independent requests using separate model copies; **KV cache** holds attention state for requests. `TP2 × 4 replicas` uses eight GPUs. Fitting weights in memory is necessary but insufficient: requests, temporary workspaces and runtime buffers also need room.

## 1. Beyond the Baseline: Llama 3.3 70B on PowerEdge

[Paper](https://infohub.delltechnologies.com/en-us/t/beyond-the-baseline-llama-3-3-70b-inference-on-dell-poweredge-servers-with-nvidia-rtx-pro-gpus/)

**Published experiment:** Llama 3.3 70B through NVIDIA NIM, measured with AIPerf, on two L40S GPUs, two RTX PRO 6000 GPUs and eight RTX PRO 4500 GPUs. Primary results mix FP8 and NVFP4. Three input/output profiles span 256/128 to 4,096/1,024 tokens. These are comparisons of selected server deployments; the serving choices need much better isolation before explaining the differences as hardware effects.

| Issue and impact | What we are doing differently / how to improve the experiment |
|---|---|
| **B1 · High · Confirmed — Precision, TP and run selection are confounded.** TP is explicitly not recorded as a controlled variable. The primary R770 result uses a different repeat-selection rationale after another run suffered severe latency degradation. **Impact:** the hardware ranking incorporates deployment and selection effects; a buyer cannot identify what produced the gain. [Stack](https://infohub.delltechnologies.com/en-us/l/beyond-the-baseline-llama-3-3-70b-inference-on-dell-poweredge-servers-with-nvidia-rtx-pro-gpus/software-stack-33/) | **Current approach:** engine, model variant, TP, replicas and placement are explicit search dimensions, with separate confirmation measurements. **Publication requirement:** show a matched comparison and a best-deployment comparison with equal tuning budgets and quality constraints. Diagnose the anomalous repeat and publish all repeats. This separates a hardware advantage from a configuration advantage while allowing Dell to demonstrate both. |
| **B8 · High · Disclosure gap — “NIM” does not identify the execution engine.** The accessible stack does not establish the actual backend, profile hash, optimized versus generic path, or throughput/latency profile. **Impact:** readers cannot determine whether the server used the best eligible implementation or reproduce its performance. NVIDIA documents materially different NIM profiles. [NIM profiles](https://docs.nvidia.com/nim/large-language-models/1.5.0/profiles.html) | **Current approach:** we evaluate engine candidates rather than treating a serving product name as the optimization decision. **Publication requirement:** retain NIM image digest, profile ID, backend/build, effective launch arguments and startup logs. Compare compatible optimized profiles with tuned vLLM, SGLang and TensorRT-LLM where supported. Select on measured service capacity; no engine wins by name alone. |
| **B2 · High · Disclosure gap — L40S “NVFP4” needs a verified compute path.** NVIDIA's NVFP4 checkpoint targets Blackwell. A four-bit stored checkpoint on L40S does not establish native NVFP4 execution. **Impact:** a fallback path could make the baseline look worse for software reasons, inflating the apparent generational gain. This is not proof the run was impossible. [Stack](https://infohub.delltechnologies.com/en-us/l/beyond-the-baseline-llama-3-3-70b-inference-on-dell-poweredge-servers-with-nvidia-rtx-pro-gpus/software-stack-33/), [model card](https://huggingface.co/nvidia/Llama-3.3-70B-Instruct-NVFP4) | **Publication requirement:** identify checkpoint representation, weight arithmetic, activation precision, KV precision and selected kernels separately. Give L40S its best compatible, quality-qualified baseline as well as any matched-format run. Dell gains a defensible upgrade comparison rather than a ratio that may depend on an unexplained fallback. |
| **B9 · High · Tuning opportunity — GPU count is not replica count.** Eight 32 GB GPUs do not imply eight independent 70B replicas. Even raw four-bit weights are roughly 35 GB before scales and runtime storage. Conversely, a 96 GB GPU may host a quantized 70B model independently. **Impact:** unnecessary sharding adds communication; insufficient sharding or cache headroom limits admission. [Hardware](https://infohub.delltechnologies.com/en-us/l/beyond-the-baseline-llama-3-3-70b-inference-on-dell-poweredge-servers-with-nvidia-rtx-pro-gpus/server-configurations-19/) | **Current approach:** search feasible TP/replica layouts and placement. **Publication requirement:** compare the candidate layouts below, verify resident memory and map every replica to GPU IDs and PCIe/NUMA locality. This can establish whether Dell should recommend more independent serving copies, more memory per copy, or a different GPU/server configuration for the target workload. |
| **B10 · High · Tuning opportunity — Scheduler and cache limits may determine the plateau.** Accessible results do not reveal batch-token budget, concurrent-sequence cap, actual KV capacity, preemption, prefix-cache policy or effective context limit. **Impact:** a low admission cap can strand GPU capacity; an oversized batch can improve output while worsening responsiveness. | **Current approach:** search memory, batching and sequence limits and collect queue/device telemetry. **Publication requirement:** retain effective settings and measured cache/admission counters. Sweep prefill budget and concurrency jointly, then confirm under independent arrivals. A flat throughput curve should trigger bottleneck diagnosis before it becomes a hardware limit. [vLLM tuning mechanisms](https://docs.vllm.ai/en/latest/configuration/optimization/) |
| **B4 · High · Confirmed — The reported operating point is not necessarily usable service capacity.** At concurrency 64, the long profile has mean TTFTs of 181, 20.2 and 18.1 seconds. **Impact:** higher output may coexist with an unacceptable wait to start the answer. [Comparison](https://infohub.delltechnologies.com/en-us/l/beyond-the-baseline-llama-3-3-70b-inference-on-dell-poweredge-servers-with-nvidia-rtx-pro-gpus/cross-metric-comparison-at-concurrency-64/) | **Current approach:** separate saturation output, stable arrival capacity and SLA-qualified capacity. **Publication requirement:** publish p95/p99 TTFT, answer latency, failures and offered/achieved load. Fixed-concurrency tests remain useful, but an independently arriving workload is needed to establish how much demand the server can sustain without queue growth. |
| **B3 · High · Confirmed scope limitation — Unequal systems lack a complete value denominator.** The comparison changes GPU count, total VRAM and server platform. **Impact:** a whole-server win cannot by itself identify the best purchase or the contribution of each GPU. [Configurations](https://infohub.delltechnologies.com/en-us/l/beyond-the-baseline-llama-3-3-70b-inference-on-dell-poweredge-servers-with-nvidia-rtx-pro-gpus/server-configurations-19/) | **Publication requirement:** report useful capacity per server, measured wall joule, rack unit and priced configuration. Keep the whole-system result; add normalized views with their limits. Model fit and communication make simple per-GPU division an incomplete explanation. |
| **B5 · Medium · Confirmed scope limitation — A 4,096-token prompt is not a RAG or code-quality evaluation.** It is the longest profile tested, not evidence of retrieval performance, code correctness or large-document service. **Impact:** application recommendations extend beyond the task measured. [Profiles](https://infohub.delltechnologies.com/en-us/l/beyond-the-baseline-llama-3-3-70b-inference-on-dell-poweredge-servers-with-nvidia-rtx-pro-gpus/token-profiles/) | **Current approach:** use multiple workload shapes and persona/session mixtures. **Publication requirement:** join completed quality evaluations to the chosen model and precision, then add genuinely longer contexts and representative task traces. Llama 3.3 is a reasonable controlled baseline; recommending it as the best application choice needs a quality/cost comparison with alternatives. |
| **B6 · Medium · Disclosure gap — A representative repeat is insufficient publication evidence.** The paper has data tables and a run-ID appendix, but accessible material does not establish dispersion or a complete power-sampling procedure. **Impact:** small differences and energy claims cannot be independently assessed. Four linked chapters were inaccessible; their contents are not presumed missing. | **Publication requirement:** release per-repeat data, executed manifests and synchronized system-power intervals. The paper explicitly calls its denominator system power; verify that boundary rather than incorrectly accusing it of GPU-only accounting. Show idle treatment, missing samples and uncertainty. [Definitions](https://infohub.delltechnologies.com/en-us/l/beyond-the-baseline-llama-3-3-70b-inference-on-dell-poweredge-servers-with-nvidia-rtx-pro-gpus/metrics-reported/) |
| **B7 · Low · Confirmed — Units and accessibility text are inconsistent.** “toks,” missing time units in Table 18 and incorrect platform/model names in Figure 2's accessible description weaken the presentation. **Impact:** readers can misinterpret units or hear the wrong comparison. [Results](https://infohub.delltechnologies.com/en-us/l/beyond-the-baseline-llama-3-3-70b-inference-on-dell-poweredge-servers-with-nvidia-rtx-pro-gpus/cross-metric-comparison-at-concurrency-64/) | **Publication requirement:** generate tables, captions and accessible descriptions from the approved dataset, then visually and technically proofread them. An alt-text defect is not automatically a defect in the visible chart. |

### Experiments that would make this paper materially better

1. **Resolve the deployment first.** For eight 4500s, test supported `TP2 × 4`, `TP4 × 2` and `TP8 × 1` layouts where weights plus cache fit. For two 6000s, compare `TP1 × 2` with `TP2 × 1`. For two L40S cards, establish the best supported quantization and sharding before using the baseline. These are candidates, not assertions about the paper's actual layout.
2. **Tune each profile for two objectives.** One winner maximizes sustained output; another maximizes accepted demand under a common latency/quality target. Sweep batching, cache precision/capacity and context admission. Measure cache reuse separately from cold, unique prompts. Hold CPU affinity and load-generator resources under observation.
3. **Explain the long-prompt collapse.** Record prefill time, queue residence, preemption/recomputation, active sequences and memory pressure. Repeat with a changed cache or admission limit. An intervention can distinguish a fixable scheduler/cache problem from an inherent hardware constraint.

**What Dell could say if confirmed:** “This server sustains more requests at the required response time after deployment tuning,” or “This GPU layout provides the same service with fewer GPUs.” The present evidence cannot supply a credible percentage for that improvement.

## 2. Signal65: Trusted Answers at Enterprise Scale

[PDF](https://signal65.com/wp-content/uploads/2026/09/Signal65-Insights_Trusted-Answers-at-Enterprise-Scale.pdf) • Page references count the cover.

**Published experiment:** RIKER tests answers against supplied synthetic enterprise records at 32K, 128K and 200K context. The detailed infrastructure diagram lists vLLM 0.10.2, while the study spans multiple accelerator platforms and model formats. This is principally an accuracy study. Its explicit exclusions for full RAG, autonomous workflows and isolated network causality are appropriate. Its missed opportunity is connecting accuracy to an executable, economical Dell deployment.

| Issue and impact | What we are doing differently / how to improve the experiment |
|---|---|
| **S1 · High · Disclosure gap — The leaderboard lacks a complete statistical recipe.** Repeat counts, seeds, scored-instance totals, per-item results and uncertainty are not sufficiently specified (pp. 5–7). **Impact:** small score gaps can influence model selection without showing whether they are repeatable. | **Publication requirement:** retain corpus/rubric hashes, model revisions, sampling settings, all item outcomes and repeated-run intervals. Deterministic grading does not make generated answers deterministic. Connect the completed quality evaluation to the configuration used in capacity testing. |
| **S2 · High · Disclosure gap — Context-length averages need a matched population.** The populations change from 91 to 72 to 54 configurations (pp. 7–10, 16). **Impact:** aggregate degradation can mix a context effect with a change in which models remain eligible. This is a reproducibility question, not proof the reported average is wrong. | **Publication requirement:** compare the same checkpoint/precision/reasoning configurations across lengths; publish unsupported, failed and excluded runs separately. Also report the full eligible population at each length. This helps Dell distinguish a model that degrades from a deployment that cannot serve the context at all. |
| **S3 · High · Disclosure gap — “200K tokens” needs a tokenizer and reservation policy.** Different tokenizers encode different amounts of source text; templates, reasoning and output consume context too (pp. 5–7). **Impact:** models may face different information quantities or truncation even under an apparently equal limit. | **Publication requirement:** run shared-document and native-token-budget comparisons, recording final tokenized prompts, retained evidence positions, output reservation, stopping reason and truncation. Confirm the engine's effective context/RoPE configuration. Separate wrong answers from exhaustion of a budget. |
| **S4 · High · Disclosure gap — A single stack diagram does not map the models to their actual runtimes.** H200, MI300X and RTX PRO systems are named; the detailed CUDA/vLLM stack cannot describe every accelerator path. GGUF-BF16 entries further need format/backend mapping (p. 7 and result charts). **Impact:** the reader cannot reproduce execution or connect a result to a server recommendation. | **Current approach:** model variants and engine choices are explicit. **Publication requirement:** one manifest per result with device, driver/runtime, engine/build, format, TP/replicas, attention implementation, KV dtype and effective context. Do not infer all entries used the diagram's vLLM build, or declare that build incapable solely from its age. |
| **S8 · High · Tuning opportunity — Accuracy alone does not identify the economical serving model.** Thinking modes and larger models can spend far more tokens and time for a small score gain (p. 11). **Impact:** a high-scoring model may support fewer users or cost more per correct answer than a slightly smaller alternative. | **Current approach:** measure capacity and latency across model/engine candidates. **Publication requirement:** compare configurations meeting the same task-quality floor on correct tasks per second, end-to-end latency, energy and cost. Include reasoning tokens and time to the usable answer. Preserve the accuracy leaderboard while adding the deployment decision it does not answer. |
| **S9 · Medium · Tuning opportunity — Long-context serving needs a cache and prefill study.** At 200K, weight fit alone says little about concurrent request capacity. Quantized KV state, chunking, context parallelism and prefix reuse can alter memory use, latency or accuracy. **Impact:** a model may pass one long-document test but be impractical for many simultaneous users. | **Publication requirement:** measure cold-document ingestion separately from repeated questions over cached documents, and record hit rates and eviction. Compare supported cache/parallelism settings under the same accuracy requirement. Map context lengths to feasible concurrent sessions; do not extrapolate from one successful request. |
| **S10 · Medium · Disclosure gap — Weight FP8 and KV-FP8 are different variables.** Some prose shortens the plotted KV-FP8 designation to FP8. **Impact:** readers can attribute an accuracy effect to weight compression when the changed state is the attention cache. | **Publication requirement:** label weight, activation and cache precision independently. Run paired one-variable comparisons against the same documents. This lets Dell state which memory-saving option preserves the task's accuracy rather than broadly endorsing “FP8.” |
| **S5 · Medium · Methodology limitation — Synthetic exact-answer grading needs validity checks.** Three template-generated domains and deterministic grading provide control, but do not span messy enterprise material (pp. 4–6, 21). Absence-of-answer probes do not alone define general hallucination performance (p. 18). **Impact:** reliable synthetic scores may overstate practical usefulness. | **Publication requirement:** audit numeric tolerances, valid paraphrases and set ordering; add noisy and contradictory documents. Report correct answers, justified abstentions, false abstentions and unsupported answers separately, including an always-abstain baseline. Evaluate retrieval and tool behavior in distinct tests before making those claims. |
| **S7 · Medium · Scope boundary — Network and server causality are not isolated.** The study acknowledges this (pp. 19–22). **Impact:** the infrastructure can be credited with hosting the workload, but its NICs or server topology cannot be credited with causing higher accuracy. | **Publication requirement:** if Dell wants a network-performance claim, add a communication-sensitive deployment and controlled network/placement comparison with latency and throughput. An alternate-NIC benchmark is unnecessary for the existing accuracy question; it is a separate opportunity. |
| **S6 · Medium · Confirmed — Inconsistent chart scales exaggerate visual changes.** Context charts use different axis minima; model labels are small (pp. 8–10). **Impact:** a visual comparison can suggest a larger or differently sized change than the numbers justify. | **Publication requirement:** use common scales or clearly labeled dot plots with uncertainty, plus a readable full results table. Keep distinct configurations identifiable instead of collapsing precision or thinking variants into an ambiguous model name. |

### Experiments that would make this paper materially better

1. **Build a quality-qualified shortlist.** Retain several model sizes and architectures that meet each task threshold. Use the exact served checkpoint, template and thinking policy. A newer or larger model is a candidate, not an automatic upgrade.
2. **Benchmark the costly part of the workload.** For each shortlisted model, test unique long documents, multiple questions over a shared document, and a mixed production arrival stream. Sweep compatible engines, TP/replicas, context admission and cache settings. Report prefill and decode separately, then the complete response.
3. **Publish the accuracy/capacity tradeoff.** Show correct completed tasks per server and per joule at the target latency. Record whether a lower-memory precision preserves accuracy at 200K, not just at short context.

**What Dell could say if confirmed:** “These configurations meet the same enterprise-answer threshold; this one serves more simultaneous document workloads or costs less per correct task.” The existing study is not evidence that vLLM was the slowest engine, and it does not claim to measure speed. The improvement is adding the missing deployment decision.

## 3. Prowess: Xeon E-cores, P-cores and “AP-cores”

[Dell report](https://infohub.delltechnologies.com/en-us/p/benefits-and-comparison-of-intel-r-xeon-r-processors-with-e-cores-p-cores-and-ap-cores-for-select-workloads/) • [Methodology PDF](https://prowessconsulting.com/wp-content/uploads/2026/05/250111-Dell-PowerEdgeR770-E-vs-P-vs-AP-core-workload-targeting-methodology.pdf)

**Published experiment:** web serving, ResNet-50 and NAMD on dual 6740E, 6767P and 6978P systems. These differ in core count, power envelope and memory configuration. The issues extend beyond insufficient tuning: the architecture description, executable procedure and result tables contain contradictions. Our project is an inference-sizing harness, so the CPU workload experiments below are audit recommendations rather than claims that capsim already runs Apache or NAMD.

| Issue and impact | What we are doing differently / how to improve the experiment |
|---|---|
| **P1 · Critical · Confirmed — AP is presented as a third core architecture.** The tested 6978P is a P-core processor/platform; the paper's heterogeneous scheduling explanation does not describe mixed core types inside these tested CPUs. **Impact:** Dell's workload-placement rationale starts from an incorrect hardware explanation. [Intel nomenclature](https://edc.intel.com/content/www/xl/es/design/products-and-solutions/processors-and-chipsets/birch-stream/xeon-6900-6700-6500-series-processors-with-p-cores-specification-update/nomenclature/) | **Publication requirement:** describe the actual CPU/platform families and distinguish fleet workload placement from scheduling inside one processor. Tie claims to measured systems and effective topology. Correct this explanation before using it in customer guidance. |
| **P2 · Critical · Confirmed procedure defect — NAMD's CPU mask uses a count as an ID.** `numactl -C $NUM_CPU_CORES` selects a CPU ID/list, not that many cores (methodology p. 9). **Impact:** the printed command does not represent the intended parallel placement. Actual runs may differ, and NAMD's own affinity flags can interact with the mask. [numactl source](https://github.com/numactl/numactl/blob/master/numactl.c) | **Publication requirement:** archive the actual command, explicit CPU lists, thread affinity and memory placement. Verify with runtime observations. Do not assert that all published runs used one core without the executed logs; require evidence that the stated experiment was performed. |
| **P5 · High · Confirmed — The efficiency table contradicts itself.** Comparator direction differs between caption and headers; the INT8/batch-1 maximum is below its minimum. **Impact:** the magnitude and direction of a purchasing-relevant advantage are unclear (report Table 2). | **Publication requirement:** regenerate the table from raw work and synchronized power data with explicit denominators. Check extrema and comparison direction automatically. Our internal audit also requires single-source generation of figures and prose. |
| **P7 · High · Confirmed — Measurement provenance conflicts.** The narrative describes tests; the legal notice describes simulated results. **Impact:** buyers cannot tell which conclusions are empirical. This could be boilerplate and is not evidence of fabrication. | **Publication requirement:** label measured, simulated and derived quantities individually and retain their source IDs. Correct the notice or identify the simulated portions. |
| **P6 · High · Disclosure inconsistency — OpenVINO is named, but the method installs Intel TensorFlow.** Appendix B points to TensorFlow reference scripts and unpinned packages/repository state. **Impact:** readers do not know which engine generated the ResNet results, let alone whether it was appropriately optimized. | **Publication requirement:** identify the actual backend per row, archive the commit/build and compare supported Intel TensorFlow/oneDNN and OpenVINO paths under equivalent accuracy constraints. Engine selection must be a measured decision. Do not claim an OpenVINO gain from a TensorFlow run. |
| **P10 · High · Tuning opportunity — Thread sweeps do not establish effective inference parallelism.** `CORES_PER_INSTANCE` and `OMP_NUM_THREADS` are swept, but the inner script/runtime can override or reinterpret them; synchronous/throughput paths also differ. **Impact:** oversubscription or poor NUMA placement can hide CPU capacity. | **Publication requirement:** capture effective threads, streams, instances, affinity and per-socket memory locality. Compare latency and asynchronous throughput modes deliberately. OpenVINO's documented hints choose different scheduling behavior; more threads alone is not a tuning strategy. [OpenVINO scheduling](https://docs.openvino.ai/nightly/openvino-workflow/running-inference/inference-devices-and-modes/cpu-device/performance-hint-and-thread-scheduling.html) |
| **P11 · High · Tuning opportunity — Precision labels do not verify the accelerated kernel.** FP32/INT8 tests do not show effective AMX/oneDNN dispatch, a BF16 comparison, or the accuracy cost of quantization. **Impact:** the study can miss a major strength of a P-core platform or compare quality-unequal workloads. | **Publication requirement:** capture kernel/primitive diagnostics, effective math precision and accuracy; compare FP32, BF16 and INT8 where supported. Use the same accuracy target, plus a matched-precision baseline. OpenVINO documents accelerated lower-precision CPU paths, but that does not prove this paper used them. [CPU precision support](https://docs.openvino.ai/nightly/openvino-workflow/running-inference/inference-devices-and-modes/cpu-device.html) |
| **P3 · High · Confirmed interpretation limit — Offered web rate is mistaken for demonstrated capacity.** wrk2 uses fixed `-R` demand; 10–100 client threads are bound to four CPU IDs (methodology pp. 5–6). **Impact:** servers can deliver equal requested work while having very different remaining capacity; an overloaded client can further hide server headroom. | **Current approach:** distinguish offered demand from achieved service and check generator tardiness. **Publication requirement:** use a verified independent generator, sweep demand through the latency/error boundary and record client scheduling lag. wrk2 is an appropriate constant-rate tool with coordinated-omission-aware measurement; the issue is interpretation and missing execution evidence, not its use. [wrk2](https://github.com/giltene/wrk2) |
| **P12 · High · Disclosure gap — Apache's serving configuration is largely unspecified.** Installation steps do not establish MPM, worker limits, keepalive, payload, TLS, cache policy or whether client and server contend for resources. **Impact:** an application or generator ceiling can be mislabeled a CPU comparison. | **Publication requirement:** freeze the full HTTP workload and server settings, verify status/error counts and connection behavior, and tune each platform within equal rules. Report a realistic service configuration and a separately identified microbenchmark. This lets Dell recommend capacity rather than a shared configuration ceiling. |
| **P4 · High · Confirmed design limitation — NAMD throughput increases almost in proportion to allocated cores.** Thirty eight-core jobs versus sixteen use 1.875× as many cores. Reported 1.84–1.87× aggregate gains imply about 0.981–0.997× throughput per allocated core. **Impact:** this supports density more directly than per-core superiority. | **Publication requirement:** publish whole-system density, time to finish one job, throughput per core and measured energy separately. Match job inputs and accuracy/integration settings. Memory bandwidth and platform differences remain relevant even after per-core normalization. |
| **P13 · High · Disclosure gap — The printed NAMD sweep does not reproduce the reported concurrent-job experiment.** Appendix C varies one invocation's threads; the launch/pinning recipe for 16 or 30 simultaneous jobs is not established. Build variants are named without a complete executed manifest. **Impact:** the central density result is not runnable from the procedure. | **Publication requirement:** provide the concurrent launcher, disjoint CPU masks, NUMA memory rules, build/version, input hashes, warm-up and timed steps. Sweep jobs-per-socket and cores-per-job independently. CPU-only NAMD is a legitimate CPU comparison; adding GPUs would answer a different question. |
| **P8 · Medium · Confirmed — Memory capacity and bandwidth are conflated.** Prose says the AP system has more memory; tables show 1,536 GB versus 2,048 GB, with different DIMM/channel/rate arrangements. **Impact:** an important source of performance and power differences is explained incorrectly. | **Publication requirement:** describe capacity, channels, DIMMs per channel and measured operating speed separately. Include a configuration-matched sensitivity test where possible, and retain the best supported full-platform result. |
| **P9 · Medium · Confirmed — Typography makes the procedure non-executable.** Smart quotes, placeholders and incomplete selections appear in the scripts (methodology pp. 4–9). **Impact:** a lengthy methodology still cannot reproduce the experiment reliably. | **Publication requirement:** publish syntax-checked scripts and a frozen software manifest. Keep typographic styling out of executable code and test the downloadable package from a clean environment. |

### Experiments that would make this paper materially better

1. **ResNet:** verify the actual runtime, then compare per-socket instances, asynchronous streams, batch size, effective precision and NUMA binding. Measure both images/s and latency at a common accuracy level. Verify the kernels that execute instead of inferring them from installed oneAPI packages.
2. **Web:** establish a generator with surplus capacity, pin it appropriately, freeze Apache and request semantics, and increase offered rate until a declared p99/error boundary is crossed. Show energy at matched useful throughput as well as maximum capacity.
3. **NAMD:** repair and verify affinity, then measure both strong scaling of one simulation and throughput scaling of many simulations. Archive the exact multicore/AVX-512 executable and job launch map. Keep the problem sizes and scientific settings fixed.

**What Dell could say if confirmed:** “This system delivers the lowest measured energy at the required web demand,” “This inference configuration reaches more images/s within latency and accuracy limits,” or “This platform completes more simultaneous simulations per rack unit.” Those are stronger and more precise than assigning broad workloads to an invented third core type.

## 4. PowerEdge R770 with RTX PRO 4500: enterprise inference

[Paper](https://infohub.delltechnologies.com/en-us/t/dell-poweredge-r770-with-nvidia-rtx-pro-4500-accelerating-enterprise-ai-inference/)

**Published experiment:** four 32 GB RTX PRO 4500 GPUs; Qwen3-8B on vLLM 0.17.1-cu130 and Qwen3.5-27B/35B-A3B on vLLM 0.19.0-cu130, all described as BF16 with four TP1 replicas. Metrum Insights 3.9 supplies the concurrency/input/output sweep. The larger-model deployment description must be corrected before its performance can be interpreted.

| Issue and impact | What we are doing differently / how to improve the experiment |
|---|---|
| **R1 · Critical · Confirmed — The published BF16 replicas do not fit.** Approximate weights alone are 54 GB for 27B and 70 GB for 35B, exceeding each 32 GB GPU. Three billion active MoE parameters do not mean only three billion parameters reside in memory. **Impact:** undisclosed quantization, sharding or offload materially changes the experiment. [Methodology](https://infohub.delltechnologies.com/en-us/l/dell-poweredge-r770-with-nvidia-rtx-pro-4500-accelerating-enterprise-ai-inference/methodology-200/), [hardware](https://infohub.delltechnologies.com/en-us/l/dell-poweredge-r770-with-nvidia-rtx-pro-4500-accelerating-enterprise-ai-inference/the-r770-rtx-pro-4500-platform/) | **Current approach:** search model variant and launch topology explicitly. **Publication requirement:** preflight physical fit, then verify actual residency, GPU map and effective precision from logs. Correct the published topology or disclose offload and its CPU/PCIe cost. A successful response alone cannot validate the stated deployment. |
| **R2 · Critical · Confirmed — Aggregate output is divided by one GPU's average power.** The 8B example uses 5,219/151 = 34.5, then suggests platform efficiency scales up again. For aggregate four-GPU output, 5,219/(4×151) = **8.64 tok/J**. **Impact:** efficiency and economic conclusions are overstated or mislabeled. [Calculation](https://infohub.delltechnologies.com/en-us/l/dell-poweredge-r770-with-nvidia-rtx-pro-4500-accelerating-enterprise-ai-inference/qwen3-8b-detailed-baseline/3/) | **Publication requirement:** match work and energy over the same devices and time interval. Whole-server efficiency needs wall power. If the numerator were per-GPU instead, relabel it and the aggregate result; efficiency still does not multiply by four when both output and power scale together. |
| **R3 · High · Confirmed — Summary and detailed efficiency values disagree.** Table 8 gives 8.5/3.2/6.1; prose gives 34.5/12.8/21.9. Using the detailed four-GPU powers yields about 8.64/3.20/5.47. **Impact:** a global divide-by-four does not reconcile every result. [Comparison](https://infohub.delltechnologies.com/en-us/l/dell-poweredge-r770-with-nvidia-rtx-pro-4500-accelerating-enterprise-ai-inference/cross-model-comparison/) | **Publication requirement:** rebuild each value from its actual measurement window, then regenerate all figures and claims. Retain the token-count source and energy boundary. This prevents an apparent hardware advantage from being an accounting difference. |

### Experiments that would make this paper materially better

1. **Establish feasible layouts.** Keep `TP1 × 4` as a natural BF16 8B candidate. For BF16 27B, compare `TP2 × 2` and `TP4 × 1` where runtime headroom allows. BF16 35B requires more than a pair of 32 GB GPUs under ordinary full residency; `TP4 × 1` is a candidate. Quantized alternatives may allow more replicas. FP8 35B still exceeds 32 GB in approximate weights alone; “FP8” is not an automatic TP1 solution.
2. **Tune for the architecture.** Qwen3.5 uses a hybrid architecture; verify its attention/state and MoE kernels, actual state-memory allocation and supported precision. Test expert-parallel alternatives only where supported and measure their communication cost. Do not apply a dense-model cache estimate blindly.
3. **Optimize usable work.** Compare common short-answer, decode-heavy and long-input workloads; include thinking and non-thinking settings where applicable. Tune prefill, active requests and batching, then confirm the winner under a common quality/latency target. Check whether CPU offload, if actually used, dominates PCIe traffic or CPU time.

**What Dell could say if confirmed:** “The selected model and precision deliver this task quality on four affordable GPUs, at this measured service capacity and energy.” A smaller model or more replicas may be the better purchase. The current contradictory memory and power descriptions prevent a trustworthy answer.

## 5. Principled Technologies: XE7740 agentic AI

[Web report](https://www.principledtechnologies.com/Dell/PowerEdge-XE7740-agentic-AI-performance-0726/) • [Report PDF](https://www.principledtechnologies.com/Dell/PowerEdge-XE7740-agentic-AI-performance-0726.pdf) • [Science appendix](https://facts.pt/QiTwFPe)

**Published experiment:** four, six and eight RTX PRO 6000 GPUs; vLLM 0.20.0; Llama 3.1 70B FP8 for text and Qwen3.5-2B for vision; LangGraph/LangChain workflows and PostgreSQL. The appendix defines fixed-concurrency workflow execution and gives substantial system detail. Its largest technical opportunities are clarifying the unit called an agent, testing realistic demand, improving GPU allocation, and identifying whether CPU/database work limits scaling.

### Experiments that would make this paper materially better

1. **Test topology before scaling claims.** For finance, compare `TP1 × 4/6/8` where the exact 70B FP8 deployment fits with sufficient cache, against the paper's TP2 layouts. Pin workers and memory near their GPUs. Then compare compatible tuned engines. For manufacturing, allocate text and vision resources according to measured phase demand rather than assuming a fixed split is optimal.
2. **Make task execution auditable.** Publish a small trace set showing input, stages, tool decisions, model calls, timestamps, outcome and GPU assignment. Distinguish adaptive execution from deterministic graphs. A controlled package and traces can enable verification without publishing proprietary source code.
3. **Measure arrivals and successful departures.** Use tasks/minute with independently scheduled arrivals, explicit workflow probabilities and burst tests. Report offered, admitted, completed, failed and abandoned work, plus backlog. For a stationary system, mean concurrency relates to arrival rate and mean residence time; a percentile latency or token rate cannot simply be converted into “users.”
4. **Find the non-GPU limit.** Profile CPU computation, SQL, orchestration and response processing. Repeat after changing one suspected limiting resource. If finance is CPU/database-limited, the useful recommendation may be a different CPU, memory/storage setup or fewer GPUs—not another accelerator.

**What Dell could say if confirmed:** “This configuration completes a defined mix of correct manufacturing/financial tasks within the stated latency, at this arrival rate and cost per task.” This is a much more portable customer promise than a single count of agents.

## What our own evidence adds—and what we must tighten

The project's implemented distinctions are substantive: separate saturation and partly-open session tests; arrival-rate and queue-stability analysis; persona latency thresholds; engine/topology/configuration search; confirmation measurements; and per-device telemetry. Source: [algorithm](docs/algorithm.md), [search](simulator/search.py), [confirmation](simulator/roofline.py), [metrics](docs/metrics.md).

Our engine notes also show why tuning must be empirical. They record a TensorRT-LLM 70B case where enabling chunked prefill reduced the observed cache pool and output from 37,494 to 18,397 tok/s, and another where postprocessing workers reduced output to 19,393 tok/s. The same notes explicitly retract an earlier attribution to CUDA graph width because two settings had changed together. These are **internal engineering observations, not a claimed speedup over any reviewed paper**, and need attached run IDs/raw evidence before customer publication. [Engine notes](simulator/engine_notes.py)

A retained [TensorRT-LLM run](exports/xe7740_sizing/runs/Llama-3.3-70B-Instruct-NVFP4__trtllm__tp1x8__run_421.json) makes the scope distinction concrete: eight 96 GB RTX PRO 6000s, Llama 3.3 70B NVFP4, TP1 × 8, 128/128 tokens, forced output length, no think time and no enforced SLA. Its stored peak is 37,445.1 generated tokens/s with p95 TPOT 222.85 ms. That is a saturation observation. Its hardware, workload and acceptance conditions differ from these papers; dividing it by a paper's number would not establish our improvement.

**Before publication, our project must pass the same audit.** The separate [internal audit](docs/audits/2026-09-26/internal-project-audit.md) documents token/chunk accounting, missing-data acceptance, configuration export and quality-linkage controls that need correction or enforcement. The stronger methodology does not excuse those defects. A search result labeled “ok” is not automatically a valid headline or an SLA pass.

The essential release package is: exact model/engine/hardware identity; executed settings and device map; task and load definitions; all trials and failures; quality evidence; synchronized latency/work/energy accounting; and an independent confirmation of the recommended operating point. This is what turns a plausible optimization into a defensible Dell claim.

## Review boundaries

All five publications were reviewed along with the complete Signal65 and PT PDFs, PT's science appendix, Prowess's separate methodology and accessible Dell chapters. Key figures and code listings were visually checked. Arithmetic was independently recomputed; no vendor benchmark was rerun. Beyond the Baseline's Tool, Concurrency sweep, NIM profile impact and Appendix D chapters were inaccessible because of retrieval/browser challenges. Their contents are not presumed absent.

Current engine documentation supports the proposed tuning mechanisms, not claims that every feature was available in every paper's tested release. Any rerun must use a pinned, compatible build. Relevant primary references include [NIM profiles](https://docs.nvidia.com/nim/large-language-models/1.5.0/profiles.html), [vLLM tuning](https://docs.vllm.ai/en/latest/configuration/optimization/), [SGLang tuning](https://docs.sglang.io/docs/advanced_features/hyperparameter_tuning), and [TensorRT-LLM runtime controls](https://nvidia.github.io/TensorRT-LLM/performance/performance-tuning-guide/useful-runtime-flags.html). These describe tradeoffs: batch size, cache allocation, scheduler policy and parallelism must be selected for the actual objective, not universally maximized.
