What is under test

Throughput vs concurrency

The saturation curve: sustained output rate at each offered stream count. It climbs while the engine can still batch more work and flattens when something binds — KV capacity, memory bandwidth, or the engine's own batch ceiling. The peak is the headline number.

Offered vs actually held

Streams offered against streams the engine really ran. While the two track, added concurrency is being served; once held flattens below offered, the extra streams are only queueing and latency grows for nothing. That gap is the engine's ceiling, and it is why a headline number needs a stream count beside it.

Latency vs concurrency

What the throughput costs. p95 time to first token and per-output-token, at each rung. No SLA is enforced on a headline run — this is the price beside the number, so a figure quoted at 8k streams can be read alongside what a user waiting on it would feel.

Power & efficiency

GPU package power, chassis power where IPMI allows it, and output tokens per watt. Efficiency is the figure that survives a hardware refresh, and a rack with a power budget is bounded by it rather than by peak throughput.

GPU — compute and memory pressure

SM occupancy against memory-controller busy, averaged over the box. At large batch a decode workload is bound by KV traffic rather than arithmetic, so the memory line saturating while SM sits lower is the normal signature — and the reason more concurrency stops helping.

Memory

VRAM in use across the box, host RAM, and the engine's resident set. VRAM flattening at the configured fraction is expected; host RAM climbing during a run is not.

CPU

Host utilization and core frequency. On a GPU-resident engine the CPU should stay modest; a busy CPU during decode usually means the load generator, not the engine, is the thing being measured.

Per-GPU detail

Per device: SM utilization, VRAM, memory-controller busy, power, temperature and PCIe traffic. An outlier here — one card throttling, or one holding far less VRAM — means the replicas are not equivalent and the whole-box number is being set by the slowest.

Sessions, in-flight & queue

Most sessions are reading or thinking at any moment, so in-flight sits well below the session count. The queue line is the engine's own waiting-request gauge — flat or empty means stationary; a steady climb at fixed arrival rate is the collapse signature the open-loop search hunts for.

Time to first token · rolling p50 / p95

Computed over the trailing turns of the measuring window. Rising p95 with a flat p50 is the first sign of queueing.

Time per output token · rolling p50 / p95

Decode pacing per token. Degrades when batches widen past the engine's comfort point.

Engine & host utilization

KV cache is the engine's own gauge; CPU is the bound-set (pinned cores only); GPU is SM utilization averaged across devices. Absent lines mean that collector isn't available on this host.

Token rates · prefill vs decode

From the engine's own counters. Prefill (prompt ingest) is compute-bound; decode (generation) is memory-bandwidth-bound — spiky prefill with sagging decode is the query-storm signature.

Session states

Where every session in the pool is right now: in prefill, streaming (decode), warm think (mid-conversation — their KV is the prefix cache's hot set), or cold (fresh sessions, nothing cached).
